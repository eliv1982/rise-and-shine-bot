# R&S-FIX-03 — Visual Diversity

**Date:** 2026-11-19  
**Repository:** `eliv1982/rise-and-shine-bot`  
**Branch:** `main`  
**Baseline HEAD:** `d4999cb9de1fdbc9b4997d0cbc2140989097a65c`  
**Status:** Owner-approved product and architecture contract for phased implementation.  
**Source:** R&S-FIX-03 Phase 0 read-only architecture audit, reviewed by Teya and Owner.

## 1. Objective

Improve the consistency, diversity and aesthetic quality of images generated by Rise and Shine across manual generation, Profile generation, More and scheduled subscriptions.

The system must respect explicit user preferences, maintain recognizable visual styles, prevent unintended scene substitution and produce varied compositions within the selected visual direction.

The purpose is **not** to eliminate recurring themes users enjoy. Recurrence of a preferred environment is acceptable; near-identical compositions and unintended routing are not.

**Core principle: diversity without losing user intent.**

## 2. Scope, exclusions and safety invariants

### In scope

- Positive versus negative coastal-intent handling; boundary-safe detection.
- Scene/style compatibility and final image-prompt integrity.
- Visual taxonomy, style descriptions and scene-preset completeness.
- Trustworthy visual memory and diversity selection.
- Expanded nature and geological environments, including tropical coastal scenery.
- Default clear-air Living Nature rendering.
- Better office, home, cafe and interior aesthetic variety.
- Symbolic/mandala compatibility, legacy identifier treatment and relevant navigation checks.
- Consistency across manual generation, Profile, More and scheduled subscriptions.

### Out of scope

- Text or image model replacement.
- Billing, subscription scheduling, delivery claims or accounting changes.
- Database schema migrations, historic data deletion, or newly stored user preferences.
- Changes to FIX-04 language ownership and text-generation contracts.
- Changing Profile generation away from its current illustration default.
- New paid planner/reviewer model calls.
- MoodMuse-specific fantasy improvements.
- Unrelated UX backlog (including `/language` duplicate acknowledgement and repeating deterministic gentle step).

### Invariants

- `users.language` governs UI and manual content; `subscriptions.language` governs scheduled content, independently of current UI language.
- Existing subscriptions, profile settings, data and generated text behavior must be preserved.
- Sea, ocean and beaches remain valid, desirable visual subjects — **never globally suppressed**.
- No additional model cost is authorized merely to choose scenes.
- No production changes without separate Owner approval.

## 3. Visual architecture

Visual decisions must be logically separable across these axes (reuse existing structures where practical):

1. **Mode:** photo, illustration, mixed, symbolic.
2. **Style:** selected or resolved visual treatment.
3. **Scene family:** nature, coast, urban, rural, interior, workspace, botanical, symbolic, etc.
4. **Environment:** specific setting (volcanic plateau, tropical lagoon, alpine lake, etc.).
5. **Composition:** framing, viewpoint, scale, visual perspective and foreground/background.
6. **Atmosphere:** light, palette, weather, aesthetic mood.
7. **Preferences and exclusions:** explicit current user intent and currently applicable stored settings.
8. **Diversity policy:** selection of compatible alternatives informed by trustworthy history.

Existing photo-style keys that imply a subject family (e.g. `sea_coast_photo`) remain supported. Separation of axes means preserving their intended constraints, not removing their identity.

No new database schema is required or authorized.

## 4. Intent, compatibility and precedence

Apply the following priorities to **semantically applicable and correctly sourced** inputs:

1. Explicit user exclusions.
2. Explicit positive user scene requests, subject to exclusions.
3. Explicit user-selected mode and visual style; if incompatible with the requested subject, do not silently violate either constraint.
4. Persisted preferences that are applicable under the existing generation path and contract.
5. Automatic recommendations and sphere-derived defaults.
6. General fallbacks.

When positive requests, exclusions and selected styles conflict, do not invent positive intent or force an incompatible scene. Prefer a compatible alternative and preserve existing app interaction semantics; report unresolved ambiguity rather than silently overriding user intent.

System-generated prompt prose, `Avoid` fields, default anti-cliche wording and other auxiliary negative lists **must never serve as evidence of positive user coastal intent**.

FIX-03 does not silently expand the current textual scope of Profile `avoid_topics` or `avoid_words` into a new global visual-exclusion feature. Any such expansion requires separate approval.

## 5. Coastal policy

Coast is a first-class supported family, **not** a mandatory default or a banned subject.

Supported environments and viewpoints include:

- Tropical palm beaches.
- Bright island shorelines.
- Turquoise lagoons and secluded bays.
- Sandy beaches and natural dune systems.
- Rocky ocean shorelines and dramatic cliffs.
- Coastal trails, viewpoints and terraces.
- Piers, harbors and seaside promenades.
- Sunrise, bright midday, golden hour and evening coasts.

Tropical scenes may evoke the Philippines: lush palms, clear turquoise water, tropical islands, white or golden sand, limestone cliffs and vivid natural light. Do not assert a specific location when one has not been explicitly requested or grounded in the selected scene.

### Required routing examples

| Input | Required interpretation |
|---|---|
| `Avoid beach` | No positive coastal intent; beach exclusion applies to the relevant scene choice |
| `Without ocean` | No positive coastal intent |
| `Без моря` / `Не хочу пляж` | No positive coastal intent |
| `Море без пляжа` | Ocean permitted; beach excluded |
| `Avoid beach, show rocky coast` | Rocky coast permitted; beach excluded |
| `Ocean view, no sandy beach` | Ocean view permitted; sandy beach excluded |
| `I want a tropical beach` | Tropical beach permitted |
| `Хочу океан и пальмы` | Tropical ocean setting permitted |
| `research`, `seasonal`, `seated`, `берегу себя` | No coastal signal from incidental substrings |

A generic anti-cliche restriction must not prohibit an explicitly selected beach. A concrete non-coastal selection must not be turned coastal by downstream photo augmentation.

## 6. Nature and geological taxonomy

Living Nature must support meaningful variety among:

- Mountain ranges, ridges, high-altitude viewpoints and alpine panoramas.
- Volcanoes, craters, lava formations and volcanic terrain.
- Valleys, canyons, gorges and dramatic topographic transitions.
- Natural terraces, unusual geological formations and rock plateaus.
- Mountain trails, expansive paths and elevated viewpoints.
- Forests, meadows, grasslands and wildflower fields.
- Lakes, rivers, streams and waterfalls.
- Coasts, beaches and tropical island environments.

Scene families should have compatible variation in distance, camera angle, framing, scale, lighting and composition. Do not hardcode a particular environment into unrelated styles or moods.

Default Living Nature visuals should favor **clear, visually legible air** rather than automatically adding haze, mist or fog. Explicitly requested fog remains supported; deliberately misty styles such as `ethereal_landscape` retain their identity.

## 7. Interior, workspace and urban aesthetics

Interior, home, cafe and workspace scenes must be aesthetically coherent and compatible with their declared style and purpose.

Avoid automatically repeating combinations such as desk + mug + notebook + window + plant. Provide varied architecture, materials, furnishing arrangements, lighting, spatial compositions and points of view.

Scene-specific negative wording must not prohibit an object that a legitimately selected scene requires. Career and work topics do not automatically require the same generic desktop scene.

## 8. Mandalas and symbolic imagery

`symbolic` remains a distinct visual mode, not a subcategory of ordinary illustration or mixed styles.

Mandala styles must show a recognizable, intentional **central radial composition**, not generic wallpaper, texture or unconstrained repeating ornaments.

Keep distinct identities for:

- `mandala_harmony` — centrally composed radial mandala.
- `sacred_geometry_light` — geometric central rosette/interlocking forms.
- `botanical_mandala` — radial leaves, petals and branches.
- `daily_symbol` — single visual emblem; **not required** to be a mandala.

Current modern symbolic handling is not presumed broken merely because earlier examples were poor. Investigate and fix demonstrated legacy/incompatible paths (`mandala`, `sacred_geometry`) while preserving stored records; do not globally route all illustrations through symbolic handling.

## 9. Diversity, More and trustworthy memory

Diversity applies **within the selected user direction**.

### Manual / Profile / More

- Preserve relevant mode, style and explicit subject intent.
- On More, prefer another eligible scene or composition where alternatives exist.
- Do not force a switch away from an explicitly preferred coast, mountain or other setting solely to create variety.
- Keep existing Profile preference reread on More and existing Profile default mode.

### Scheduled

- Preserve current content language, delivery claim, retry, accounting and scheduling invariants.
- Use a compatible, trustworthy visual history where it is available.
- Do not change subscription mode just to improve scenery diversity.

### History and rotation

- Distinguish **actually used** scenes from shadow-only plans.
- Do not treat exclusion text (`Avoid beach`, `no human`) as positive observed motifs.
- Prefer representation of effective final image request when recording new scene metadata.
- Read legacy history safely; no clearing, migration or destructive rewrite.
- Use deterministic selection where practical for testability; it does not guarantee perceptual image uniqueness.
- Do not introduce new persistent state or extra paid model calls.
- Define expected behavior when eligible alternatives are exhausted; no infinite retry loops.

## 10. Phased implementation and acceptance gates

### FIX-03A — Coastal Intent Integrity

**Scope:** correct source-aware positive coastal intent, negation and word boundaries, scene-level exclusions and unintended final photo augmentation across relevant generation paths.

**Acceptance:**

- Negative-only inputs do not activate coast; explicit coast remains available.
- Mixed positive/negative cases retain the requested compatible coast while excluding the prohibited subtype.
- False substrings do not trigger coast.
- Controlled forest/workspace prompts containing default `Avoid beach` remain non-coastal in the **effective image API payload**.
- Intended tropical beach and rocky coast scenes remain valid.
- Existing public interfaces are preserved where feasible; tests cover controlled, template and enriched paths with mocked provider.
- No implementation of FIX-03B–03E occurs in this phase.

### FIX-03B — Taxonomy Integrity

**Scope:** restore missing active style descriptions; reconcile candidate pools, scene definitions, family normalization, subject/avoid conflicts and composition compatibility.

**Acceptance:**

- Every active selectable style has an effective description.
- Selectable scene candidates have valid definitions or intentional documented fallbacks.
- Scene/style and scene/composition combinations are coherent.
- No mutually contradictory positive/negative scene instructions reach final payload.

### FIX-03C — Diversity and Memory

**Scope:** improve interpretation of actual scene history, anti-repeat choice and consistent application to manual/More/scheduled without schema changes.

**Acceptance:**

- Negative and shadow-only references do not masquerade as generated scenes.
- Eligible alternatives are considered on repeated generation.
- Repetition under exhausted candidate pools is handled safely and explicitly.
- Retry, restart, legacy data, Profile → More and scheduled semantics remain intact.

### FIX-03D — Visual Enrichment

**Scope:** richer nature/geology/coast environments, viewpoint diversity, clear-air contract and stronger interior/workplace aesthetics.

**Acceptance:**

- New families are reachable through intended selectors, not only present in text tables.
- Volcanoes, mountain panoramas, terraces, canyons, rivers/lakes, forests and tropical palm beaches are meaningfully represented.
- Clear-air nature behavior is consistent across relevant paths, without banning intentionally misty scenes.
- Interiors/workspaces demonstrate distinct coherent compositions.
- Small Owner-approved live visual sample meets expectations; no uncontrolled paid sampling.

### FIX-03E — Symbolic/Legacy and Navigation Hardening

**Scope:** demonstrated legacy symbolic routing defects and relevant RU/EN style Back/Main menu gaps; end-to-end regression coverage.

**Acceptance:**

- Recognizable mandalas, no generic wallpaper substitution in intended mandala path.
- Legacy compatibility is non-destructive and does not leak mandalas into normal illustration/mixed recommendations.
- Back/Main menu and compatible style callbacks pass targeted tests.
- Existing FIX-04/profile/subscription behavior remains passing.

## 11. Validation, independent audit and Git ownership

For **each** implementation phase:

1. Codex develops **only the approved phase**, adding targeted deterministic tests.
2. Existing relevant regression tests run locally; providers are mocked.
3. Codex reports changed files, test counts, findings and limitations.
4. Claude Code independently reviews in **read-only** mode, including final prompt semantics and regression boundaries.
5. Any critical findings are fixed and audited again.
6. **Owner alone** performs Git status/staging/commit/push, following Teya's stepwise instructions; Codex does not perform Git operations.
7. Verify GitHub Actions CI after push.
8. No deployment without separate Owner approval.

A deterministic prompt test establishes routing integrity, not visual attractiveness. Live images are permitted only as a separately approved, limited quality assessment; no automatic bulk runs.
